# Muse Spark 1.3

## Reasoning / Thinking
- Type: **always on, cannot be turned off**. `reasoning_effort: "none"` is explicitly rejected ("Disables reasoning. Not supported by Muse Wonder or Muse Spark: returns `HTTP 400`") — every zero-thinking fast path from a predecessor model must be mapped to `minimal` or `low`.
- Parameter name depends on protocol: `reasoning_effort` (Chat Completions) vs. `reasoning.effort` (Responses API). Levels: `minimal | low | medium | high | xhigh | max`. `max` exists in the Spark line only for the standard-tier `muse-spark-1.3`, not for `muse-spark-1.3-contributor`.
- **No published default value**: without the parameter "the model still reasons at a model-determined level" — which level that is appears nowhere (unverified). Therefore always set effort explicitly in the prompt contract.
- Chain of thought is private ("The model's chain of thought is private. The raw reasoning is not returned as readable text"); on Chat Completions `reasoning_content` is redacted to empty for external callers. Summaries exist only on the Responses API via `reasoning.summary` (`auto` ≈ one sentence / `concise` / `detailed`) — and even these are not guaranteed.
- Reasoning tokens count against `max_tokens` or `max_output_tokens` and are billed with the output; reported in `completion_tokens_details.reasoning_tokens` or `output_tokens_details.reasoning_tokens`. Re-size token budgets for `xhigh`/`max`.
- Reasoning preserved across turns / tool loops: on the **Responses API** via `previous_response_id` or `include: ["reasoning.encrypted_content"]`; on the **Messages API** via Anthropic-style `thinking` replay (history kept client-side; `redacted_thinking` carries the encrypted blob and is replayed). Only Chat Completions carries no reasoning across turns ("each turn reasons from scratch").
- Meta's own effort heuristic: high effort for "proofs and calculations, complex code generation, architecture trade-off analysis", `low` for direct answers where latency and cost matter. `logprobs` is not supported (HTTP 400).

## Prompting style
- **`developer` role instead of `system`**: Meta explicitly recommends "prefer a `developer` message over the `system`" for tone, format and standing rules. When migrating, relabel the system-prompt layer accordingly rather than just copying it.
- **Effort is part of prompt design**, not merely a cost dial: for cleanly scoped tasks Meta says `reasoning_effort=xhigh` can deliver a complete artifact in a single pass — multi-step prompt choreography then becomes unnecessary.
- **Plan for or suppress clarifying questions**: the model "asks for input when needed", per the launch blog has "better calibration on what constitutes irreversible actions" and "confirms before taking consequential actions". For unattended runs, grant autonomy explicitly and supply defaults for anything underspecified.
- **Long, complex instructions are allowed**: 1.3 "follows complex, long-form instructions more reliably than earlier Muse Spark models" — preemptively splitting into mini-prompts is not necessary.
- **Tool descriptions carry the load**: "Write clear, specific descriptions for the tool and for each parameter. The model uses them to decide when and how to call the tool." No re-explaining the tools in prose in the system prompt.
- **Prompt order for caching**: "Put stable content first, such as system prompt, instructions, and examples, and put variable content last." Caching is automatic and active without setup; the order determines hit length.

## Strengths & weaknesses (prompt-relevant)
- Classification: per the model overview "the latest version" of the Muse Spark line and "Recommended for new work", "the default model in the code examples throughout these docs", available in Muse Code and the Meta Model API. Meta's most capable model per the same page (as of 2026-10-13) is Muse Wonder (`muse-wonder-1.0`, preview), which accepts the same requests on the same endpoints.
- Strengths: "Trained for long-horizon, agentic workflows" — keeps context and intermediate results, works "through messy or conflicting inputs", proactively fixes plan gaps and handles several workflows in parallel. Natively multimodal perception (image, video, documents); images as base64 data URL or public URL directly in message content, including self-inspection of rendered results and error screenshots; computer use from a plain-text goal plus screenshot without coordinates.
- Token economy: versus 1.2, per Meta roughly **20% fewer tool calls and 25% fewer tokens**, "takes fewer turns where not needed and is less verbose" — "be brief" instructions carried over from 1.2 are mostly redundant.
- "Better awareness of its own capabilities and limitations" and fewer hallucinations — defensive "invent nothing" blocks can be slimmed down. Also "stronger adversarial robustness, with improved resistance to adversarial inputs and prompt injections"; hardening against injection in the prompt remains sensible, but is no longer the only line of defense.
- Weakness (officially documented): **audio**. "Audio understanding in Muse Spark 1.3 is currently not fully supported, and response quality for requests including audio content may be degraded. For audio, use Muse Spark 1.2, or Muse Voice Transcribe for dedicated speech-to-text."
- Weakness: `tool_choice` accepts only `"auto"` — any forced tool choice (`required` or a named function) ends in HTTP 400. Tool requirements must be phrased in the prompt.
- No published knowledge cutoff and no published output-token limit (unverified). The launch blog's benchmark comparisons appear only as a chart, with no numbers in the running text.

## Output & format conventions
- Context window **1,048,576 tokens**; input text, image, video, audio (limited, see above) and PDF; output text only. Maximum output tokens are not published (unverified).
- Structured output: `response_format` with `"type": "json_schema"` (Chat Completions) or `text.format` (Responses API); "the model constrains token generation to produce only valid JSON matching your schema". `strict` defaults to `false`; with `strict: true` the root must be a plain object, every object must set `additionalProperties: false`, and `required` must list **all** keys. Recursive schemas are not supported. Limits (also apply to function-tool `parameters`; exceeding → HTTP 400): depth 10, 5,000 properties, 120,000 characters total, 1,000 enum values (default, raisable per app); string enums with more than 250 values max. 15,000 characters; schemas with more than 200,000 nodes after `$ref` expansion are rejected.
- Tool calling: `parallel_tool_calls` defaults to `true` (multiple calls per turn possible); `max_tool_calls` caps only built-in tools, not function tools; tool names must match `^[a-zA-Z0-9_.-]+$` with at most one dot. Even with `strict: true` the generated arguments are only schema-*guided* and "not guaranteed to validate against it" — keep validating server-side.
- Three protocols against the same models, same auth and same price: Responses (`/v1/responses`, Meta's "recommended default for new work", the only route for search grounding; reasoning preserved via encrypted replay or `previous_response_id`), Chat Completions (`/v1/chat/completions`, OpenAI format, no reasoning preserved across turns), Messages (`/v1/messages`, Anthropic format, history kept client-side, reasoning preserved via `thinking` replay; `thinking: {type: "disabled"}` → HTTP 400, `output_config.effort` passes only `low`–`xhigh` through).
- Prices per 1M tokens: standard $1.25 input / $0.15 cached input / $4.25 output; contributor $0.10 / $0.002 / $0.20 — the contributor tier buys the lower price with "permission to use your prompts and completions to train future Meta models". No batch discount and no price tiers by context length documented.
- Prompt caching is automatic; hits appear in `usage.prompt_tokens_details.cached_tokens` (Chat Completions) or `usage.input_tokens_details.cached_tokens` (Responses). On the Responses API, `prompt_cache_retention: "24h"` requests extended retention of up to 24 hours — a hint, not a guarantee (earlier eviction under load possible). A minimum length for cacheable prefixes is not documented (unverified).

## Migration notes
- **AWAY FROM Muse Spark 1.3**: re-add brevity, self-check and "invent nothing" instructions if the target model does not bring these properties itself; revert the `developer` message to `system` if the target has no developer role; re-define clarifying-question behavior, because target models without "asks for input when needed" simply guess on underspecified prompts — write defaults into the prompt; remove Meta-specific fields (`reasoning.summary`, `include: ["reasoning.encrypted_content"]`, `previous_response_id`) and keep conversation state client-side; recalibrate the effort ladder once the target can turn reasoning off or uses other level names; re-evaluate audio paths that were moved to Muse Spark 1.2 or Muse Voice Transcribe because of the 1.3 limitation, against the target's capabilities.
- **TO Muse Spark 1.3**: remove `reasoning_effort: "none"` and any "don't think" equivalent (HTTP 400) and map to `minimal`/`low`; set effort explicitly instead of trusting an inherited default; remove `tool_choice: "required"` or named-tool forcing (only `"auto"` is allowed, otherwise HTTP 400) and phrase the requirement in the prompt instead; remove `logprobs` (HTTP 400); raise token budgets, because reasoning tokens count against `max_tokens`/`max_output_tokens`; turn the system prompt into a `developer` message; remove verbosity and turn-saving instructions from 1.2 prompts; switch from Chat Completions to the Responses API (or, on an Anthropic stack, the Messages API with `thinking` replay) if reasoning should persist across tool loops; search grounding requires the Responses API; reorder the prompt so static content comes first; plan for `max` only if the standard tier is actually used (contributor does not know the level). Access itself is a base-URL change — from the OpenAI ecosystem `api.meta.ai/v1` plus a key swap, from the Anthropic ecosystem the Messages API against `https://api.meta.ai`.
