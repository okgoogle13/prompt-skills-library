# Kimi K3

## Reasoning / Thinking
- Type: **always on, cannot be turned off**. The quickstart FAQ, asked about disabling chain-of-thought, answers: "You can't — K3 always thinks." The only lever against excessive thinking time is `reasoning_effort: "low"`.
- Depth is controlled exclusively via the top-level field `reasoning_effort`: `low | high | max`, **default `max`** — i.e. the most expensive tier if nothing is set. Moonshot maps them as follows: `low` fastest, `high` a balance of speed and quality, `max` for the hardest tasks.
- The K2.x `thinking` object (`type: "enabled"|"disabled"`, `keep`) is **not** supported by K3; the docs, for migrating from K2.x, explicitly say to remove the old `thinking` configuration and set `reasoning_effort` instead.
- Reasoning text is returned separately from the answer text: non-streaming as `reasoning_content` in `choices[0].message`; per the quickstart, when streaming as separate deltas alongside `content` — the quickstart's streaming example reads it as `delta.reasoning_content` (the Chat Completions reference lists only `role`/`content`/`tool_calls` in the delta schema).
- Via the Anthropic-compatible Messages API the same control is called `output_config.effort` (`low|high|max`); reasoning appears there as a thinking content block in the order thinking → text → tool_use and streams as `thinking_delta`. Via the Responses API the control is called `reasoning.effort` (enum `low|high|max`, default `max`); other values are not documented.
- Set `reasoning_effort` **before** the conversation starts — Moonshot justifies this with cache reuse; `tool_choice` by contrast may change per request without invalidating the prefix cache.
- `max_completion_tokens` caps reasoning **plus** the answer: default 131,072, maximum 1,048,576. Per the agent guide, `finish_reason: "length"` should be treated as an error and the limit raised, not recorded as a finished answer.

## Prompting style
- **Keep the system prompt lean and role-focused**: "Keep the system prompt focused on the role, workflow, and quality boundaries. Leave argument details in the tool schema." Add requirements incrementally instead of monolithically up front.
- **Set boundaries explicitly**: Moonshot describes K3 as "proactive by nature — if you need tighter boundaries, set them explicitly in your system prompt or AGENTS.md". Narrowly scoped tasks need a written-out scope rule.
- **No sampling controls**: temperature, top_p, n and the penalties are fixed (see below). Determinism, variance and format adherence must come entirely from the prompt, `response_format` and tool schemas.
- **Declare tools sparingly**: "don't put every tool definition into the request — they eat up context and make the model more likely to pick the wrong tool". Recommended is a single `search_tools` function plus a few core tools; the rest is loaded on demand via Dynamic Tool Loading through a `system` message with a `tools` field (identical schema format). `tool_choice: "required"` in the first turn forces research, then back to `"auto"`.
- Keep tool schemas tight: `additionalProperties: false` plus a complete `required` list reduces invalid arguments according to the docs.
- General platform recommendations (not K3-specific): set the role in the system message, separate sections with delimiters (triple quotes, XML tags, headings), spell out work steps explicitly, use few-shots for hard-to-describe styles, set length targets as a number of paragraphs or bullets rather than a word count, and actively ask for brevity ("The model can't read your mind").

## Strengths & weaknesses (prompt-relevant)
- Strengths: long, lightly supervised engineering runs ("sustain long engineering sessions with minimal oversight, navigate massive repositories"); native image **and** video understanding in the same model; 1M context; structured output reliable per the docs, including nested objects, arrays and `anyOf`; `tool_choice: "required"` supported (the K2.7-code and K2.6 models cannot).
- Cost lever: the cache-hit price is one tenth of the cache-miss price, and Moonshot cites "90%+ cache hit rate" for coding workloads — stable prompt prefixes are the most important cost factor with K3, not prompt length.
- Weakness: **repeated identical tool calls** are a documented pattern; Moonshot provides a client-side playbook for this (reminder after 3 identical repeats, stronger reminder at 5, again at 8) rather than a model parameter — such reminders belong in the agent loop, not in the static system prompt.
- Weakness: the complete assistant turn must be returned unchanged. "Copying only `content` and `tool_calls` drops any returned `reasoning_content` and breaks the context needed by later tool calls." Likewise: "don't switch to K3 mid-session from another model."
- Other quirks: the built-in web search `$web_search` (`builtin_function`) is deprecated and will be shut off on 20.10.2026; replacements are the standalone REST APIs `POST /v1/tools/search`, `/v1/tools/search_pro` and `/v1/tools/fetch` (own web search QPS limit, separate from RPM/TPM), and on the Responses API additionally the server-side tool `{"type": "web_search"}`; public image URLs are not accepted (only base64 or `ms://<file-id>`, with `content` as an array of objects); the cache is stored in blocks — a remainder that does not fill a full block is not written and is billed as a cache miss; Tier0 (from a $1 top-up) with 1 concurrency and 3 RPM is practically only usable for testing.

## Output & format conventions
- Context window 1,048,576 tokens; `max_completion_tokens` default 131,072, maximum 1,048,576. Modalities text/image/video → text.
- **Fixed sampling parameters**: "temperature=1.0, top_p=0.95, n=1, presence_penalty=0, and frequency_penalty=0 are fixed; omit them from requests." The Messages API does not document `temperature`/`top_p` at all.
- `response_format`: `text` (default) | `json_object` | `json_schema`. Docs rule: "Always explicitly set strict: true." When parsing, read only `choices[0].message.content` — "do not call json.loads on the entire response object", and never `reasoning_content`.
- Three interfaces for K3: Chat Completions, Responses (`POST /v1/responses`, per the reference currently only `kimi-k3`) and Messages (Anthropic-compatible). On the Messages API `max_tokens` is required and the thinking block must go back unchanged into the following turn.
- Prefill/partial mode: on Chat Completions, append a final assistant message with `partial: true` and the model continues the text (prepend the prefix when displaying); on the Messages API a final assistant message is enough. Thinking consumes `max_tokens` first — too small a limit ends with empty `content` and `finish_reason: "length"`.
- Prices per 1M tokens: input $0.30 (cache hit) / $3.00 (cache miss), output $15.00; cache write billed separately at $3.00 (TTL 5 min) or $6.00 (TTL 1 h) per 1M tokens — flat, explicitly **no** tiering by context length. A minimum top-up of $1 unlocks K3; rate limits scale with cumulative top-up from Tier0 (1 concurrency / 3 RPM / 500k TPM) to Tier5 (100 / 300 RPM / 5M TPM).
- Prompt caching is automatic (no cache ID) with TTL `5m` (default) or `1h`: on Chat Completions and Responses via `prompt_cache_options: {"mode": "implicit", "ttl": "1h"}`; on the Messages API only via a top-level `cache_control` (`{"type": "ephemeral", "ttl": …}`) — if absent, reads and writes use the default `5m`; `cache_control` markers inside `messages` are ignored. An entry's TTL is fixed from its first write. `prompt_cache_key` exists on Chat Completions and, per the reference, should carry the session or task ID for coding agents — when resuming an interrupted session, keep the same value unchanged.
- Open weights: the `moonshotai` model card lists 2.8 T total parameters / 104 B active, 896 experts with 16 selected plus 2 shared per token, the MoonViT-V2 vision encoder, MXFP4 weights and the "Kimi K3 License". As an evaluation setting (not a stated recommendation) the card lists temperature 1.0 with reasoning effort `max`, with top_p 0.95 for single-step or top_p 1.0 for agentic tasks; no sampling recommendation for self-hosting is documented (unverified).

## Migration notes
- **FROM kimi-k3**: explicitly request reasoning again if the target model does not always think (step-by-step instruction, thinking toggle or reasoning budget, depending on the target); re-evaluate the K3-specific scope brakes ("proactive by nature") instead of carrying them over blindly; check the tool-repeat reminders in the agent loop — they compensate for a K3 pattern; remove `reasoning_effort`, `output_config.effort` and `reasoning_content` handling; re-introduce sampling parameters (temperature/top_p/penalties) as real controls — they were ineffective under K3; keep Dynamic Tool Loading and `search_tools` indirection only if the target documents them too.
- **TO kimi-k3**: remove `thinking` objects from K2.x as well as temperature/top_p/n/presence_penalty/frequency_penalty without replacement; set `reasoning_effort` deliberately instead of inheriting the expensive `max` default, and fix it before the first turn; resize `max_completion_tokens`, because reasoning draws from the same budget; restructure the pipeline so the complete assistant turn including `reasoning_content` is returned unchanged (otherwise follow-up tool calls break); switch format enforcement from free-text conventions to `json_schema` with `strict: true` and parse only `content`; slim down tool catalogues or move to Dynamic Tool Loading; convert image URLs to base64 or `ms://<file-id>`; remove `$web_search` declarations (shut off 20.10.2026) and connect search either as a custom function tool via `/v1/tools/search`/`search_pro`/`fetch` or via the server-side `web_search` tool of the Responses API; keep prompt prefixes stable so the 10×-cheaper cache-hit price applies; replace Claude-typical `cache_control` breakpoints on content blocks with a top-level `cache_control` (Messages API) or `prompt_cache_options.ttl` (Chat/Responses), and choose `1h` when request gaps exceed 5 min; keep Claude-style prefill (final assistant message) on the Messages API or express it as `partial: true` on Chat Completions; avoid switching models mid-session.
