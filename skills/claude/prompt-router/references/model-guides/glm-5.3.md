# GLM-5.3

## Reasoning / Thinking
- Type: **forced on**. `thinking: {"type": "enabled"}` is the only permitted value — "Disabling reasoning is no longer supported". A request with `thinking.type: "disabled"` fails; on GLM-5.2/5.1/5/4.6 the model decides itself whether to think.
- Depth exclusively via `reasoning_effort`: `low` (mild inference, only on 5.3/5.3-Flash) | `high` (enhanced inference) | `max` (deep inference; per the docs **"default and recommended"**). On the standard API endpoint any other value of the platform-wide enum produces an error ("Any other input will result in an error"); on the coding-plan endpoint `none`/`minimal`/`low` are mapped to `low`, `medium`/`high` to `high`, and `xhigh`/`max` to `max`; in the open weights a missing or unknown value silently falls back to `max` ("defaults to max if not passed (or if set to any other value)"). On GLM-5.2, `none`/`minimal` (thinking off), `low`/`medium` (→ `high`) and `xhigh` (→ `max`) were still mapped.
- There is thus **no zero-thinking path**: "Thinking process will consume extra tokens, please manage your tokens." For workloads that were previously thinking-free, re-size the token budget; `low` is the floor, not "off". Whether reasoning tokens count against the same `max_tokens` as the answer is not stated by any Z.ai source (unverified).
- Reasoning output: non-streaming as a `reasoning_content` field alongside `content`; in the stream, `delta.reasoning_content` first, then `delta.content`.
- `clear_thinking` discards the reasoning of previous turns. Preserved thinking (`clear_thinking: false`) is off by default on the standard API endpoint and on by default on the coding-plan endpoint; in the open weights' chat template `clear_thinking` is `false` — for chat scenarios the model card explicitly recommends passing `clear_thinking=true`. For coherent multi-turn runs, set it to `false` and return the historical `reasoning_content` unchanged — "All consecutive reasoning_content blocks must exactly match the original sequence", otherwise the cache benefit is lost.

## Prompting style
- Z.ai positions 5.3 as a coding and agent model ("comprehensive advancements in complex software engineering and agent capabilities") — prompt directly and task-oriented, without role prose (unverified).
- Official task scheme for agent prompts, four blocks: **Goal** (what is built or changed), **Context** (affected files, error messages, examples), **Constraints** (coding standards, architecture, security and dependency rules), **Done when** (acceptance criterion: tests green, bug no longer reproducible).
- Keep three context layers separate: task context (the prompt), project context (repo structure and engineering rules), environment context (tools, permissions, execution environment). The docs' rule: "Put temporary instructions in the prompt, and put long-lived rules in project-level configuration files."
- For complex tasks, put a **planning phase** first (explore the codebase, set scope, confirm approach) instead of requesting code immediately — per the docs, direct code requests lead to logic errors and rework.
- Keep sessions narrow: one session per task; cut long sessions by summarising; branch into a new session.
- Do **not** adjust `temperature` and `top_p` at the same time — the migration page explicitly recommends tuning only one of the two values.
- There is no GLM-5.3-specific prompt-engineering page; any style statement beyond this is unverified.

## Strengths & weaknesses (prompt-relevant)
- Strengths: agentic coding in realistic scenarios (+50% over GLM-5.2 on Z.ai Code Bench; Terminal-Bench 3.0 from 4.6 to 28.3); emergent security and vulnerability capabilities (CyberGym 84.5%, ExploitBench 54.4%); higher token efficiency per Z.ai (at max effort 34.5% at around 75K output tokens per task, versus 23.4% at 96K for GLM-5.2); 1M context and 128K output in one model; context caching with reported `cached_tokens`.
- The base, per the official model card, is **the same base model as GLM-5.2** ("same base model as GLM-5.2"); the gain comes from post-training — substantively, a 5.2 prompt carries over; only the thinking contract breaks.
- Weaknesses and quirks: **text-only** ("GLM-5.3 currently supports text-only inputs"), so no image input — the release notes list visual capabilities only for `glm-5.3-flash`; narrow `reasoning_effort` enum without `medium`/`xhigh`; effort values ported from other providers fail with an error on the standard API, but silently run as `max` when self-hosted (no error, highest cost); no published knowledge cutoff (unverified). As a third-party host, Mistral serves the model unchanged as `zai-glm-5-3` (GA, per Mistral globally and in the EU, not yet via the US endpoint); further third-party clouds are not verified (unverified).
- The migration page explicitly warns about "excessive randomness or excessive conservatism" when moving over — after migration, cross-check sampling and answer length instead of carrying over old values.

## Output & format conventions
- 1,000,000 token context window, `max_tokens` up to 128K; input text, output text.
- Sampling defaults: `temperature` 1.0 (range 0.0–1.0), `top_p` 0.95 (range 0.01–1.0), `do_sample` `true`; `stop`: the schema allows 4 entries, but per the parameter description only one stop word is currently supported ("Currently, only one stop word is supported").
- Structured output via `response_format: {"type": "json_object"}` (default `"text"`); function calling via `tools` (max. 128 functions), `tool_choice` exclusively `"auto"` ("only auto is supported") — forced or named tool choice is not available.
- Streaming tool calls requires `stream=true` **and** `tool_stream=true`; the arguments arrive incrementally and must be concatenated by the client from `delta.tool_calls[*].function.arguments`.
- Price per MTok: input $1.40, cached input $0.26, output $4.40; cached-input storage currently free (as of 2026-10-13).
- Via Mistral's API (`zai-glm-5-3`), `message.content` always comes back as a chunk list (thinking + text), regardless of `reasoning_effort` — there is no plain-string mode there; `reasoning_effort` there is `low`/`high`/`max`, not `none`.
- Release-notes entry: 2026-08-18. Model card: 753B parameters (architecture tag `glm_moe_dsa`; active parameters not stated, unverified).

## Migration notes
- **FROM glm-5.3**: target models without forced thinking need an explicit thinking setup again (toggle, budget or effort field of the target) — otherwise a 5.3 prompt runs there without reasoning; do not blindly carry over `reasoning_effort: max`, since other providers' scales are cut differently; remove `clear_thinking`, `tool_stream` and the `reasoning_content` handling, or map them to the target's conventions; re-add explicit verification and step-by-step instructions if the target does not think deeply by default; check 1M-context and 128K-output assumptions against the smaller target window; replace `response_format: {"type": "json_object"}` with the target's structured-output format.
- **TO glm-5.3**: (1) **Breaking**, official wording: "If your application currently uses `thinking.type: "disabled"`, please change it to `enabled` and set `reasoning_effort` to `low` before updating the model ID to `glm-5.3`. Otherwise, the request will fail." Every non-thinking fast path becomes `enabled` + `low`. (2) Remove `reasoning_effort` values from the GLM-5.2 era (`none`, `minimal`, `medium`, `xhigh`) — there they were mapped, here they are an error on the standard API; when self-hosted there is no error but a silent fallback to `max` — so never carry over `none`/`minimal` as "off", explicitly set `low` instead. (3) Set `model` to `"glm-5.3"` and adjust `max_tokens` to the 128K limit. (4) `temperature` 1.0 / `top_p` 0.95 as a starting point, then tune only one of the two. (5) Switch streaming tool calls to `tool_stream=true` plus argument concatenation. (6) Extend multi-turn histories with `reasoning_content` and set `clear_thinking=false` if the reasoning chain should carry across turns. (7) Multimodal routes fail — put image inputs on `glm-5.3-flash`, which per the release notes has native visual capabilities. (8) After the switch, work through the official verification checklist: answer quality, randomness and conservatism, tool streaming, and latency and cost under long context and deep thinking. (9) Reduce multiple stop sequences to one; remove `tool_choice` values other than `auto` (a replacement for forced tool choice is not documented — unverified).
