# o3

## Reasoning / Thinking
- **Type: always on (pure reasoning model).** o3 belongs to the o-series, which generates internal "reasoning tokens" before producing an answer; these tokens serve planning, tool use and multi-step problem solving. They are **not visible** through the API, are not kept in context between turns, but do occupy context-window space and are billed as output tokens.
- **Depth control via `reasoning_effort`.** The parameter controls how much the model "thinks". Documented levels: `low` (efficient reasoning with low latency overhead), `medium` (balanced point on the Pareto curve) and `high` ("Hard reasoning, complex debugging, deep planning, and high-value tasks"). Additional values such as `none`, `minimal`, `xhigh` exist depending on the model — which of these o3 supports is not explicitly listed in the primary docs **(unverified)**.
- **Why classic chain-of-thought is counterproductive here:** since o3 runs its thinking process internally, OpenAI says it is "unnecessary" to instruct the model with "think step by step" or "explain your reasoning". The o3/o4-mini prompting guide also warns that prompts such as "plan more extensively" can even **reduce** performance — the model already reasons natively, so extra meta-reasoning instructions are redundant.
- **Context budget:** when experimenting, reserve at least ~25,000 tokens for reasoning + output; `max_output_tokens` caps total generation and prevents truncated answers. The exact reasoning-token usage appears in the `usage` object under `output_tokens_details`.

## Prompting style
- **"Less is more."** o3 excels with short, clear instructions: "Keep prompts simple and direct". Too many constraints or examples can reduce accuracy.
- **Zero-shot first, then few-shot.** Reasoning models often need no few-shot examples; if used, they must align closely with the instructions.
- **High developer-message fidelity.** Developer messages are treated as explicit developer instructions and act as "durable interface contracts" — they should define clear boundaries (e.g. when a tool is called). Critical rules belong at the start of the prompt.
- **Prescriptive for complex tasks.** For multi-step flows, spell out the exact order of function calls and clear boundaries ("when to use a tool vs. answer directly").
- **Use delimiters.** Markdown, XML tags and section titles help separate input parts clearly. State clear end goals and success criteria.

## Strengths & weaknesses (prompt-relevant)
- **Strengths:** o3 is positioned as "a well-rounded and powerful model across domains" and leads in coding, mathematics, science and visual perception (SOTA among others on Codeforces, SWE-bench, MMMU; SWE-Bench Verified 69.1%). Especially strong at image, chart and graphic analysis. It can combine tools **agentically** (web search, Python data analysis, image understanding, image generation) and decides itself when and how to use tools.
- **Weaknesses / quirks:** overall o3 makes **more claims** than o1 — which leads to more correct but also more hallucinated statements; in the PersonQA evaluation this effect is more pronounced than in SimpleQA. Known tool-use quirks: the model sometimes promises future tool calls without executing them, or shows "lazy behavior" (terse answers / "no time"). Countermeasures: start fresh conversations for new topics; discard irrelevant earlier tool calls and summarize instead.

## Output & format conventions
- **Developer messages instead of system messages.** From `o1-2024-12-17` the o-series supports developer messages; system messages sent by the developer are automatically converted internally into developer messages.
- **Markdown held back by default.** To enable Markdown formatting in answers, include `Formatting re-enabled` in the **first line** of the developer message.
- **Modalities:** image as input (input only); function calling, structured outputs and streaming are "Supported". Context window: 200,000 tokens, max output: 100,000 tokens, knowledge cutoff: 1 Jun 2024 (snapshot `o3-2025-04-16`).
- **Tool / function calling:** set `strict: true` so schemas are followed reliably; encode "when to call this function" directly in the function description (not only in the developer prompt). In-distribution are setups with fewer than ~100 tools and fewer than ~20 arguments per tool. Persist chain-of-thought between tool calls via the Responses API with `include=["reasoning.encrypted_content"]`.

## Migration notes
- **Deprecation:** `o3-2025-04-16` is scheduled for shutdown on 11 Dec 2026 per OpenAI's deprecations page; official replacement `gpt-5.6-sol`. New migrations TO o3 only as a stopgap. (The o3 model page additionally names GPT-5 as successor — its snapshot `gpt-5-2025-08-07` is shut down on the same day.)
- **TO o3**: **remove** explicit "think step by step" / CoT instructions and planning scaffolding carried over from GPT prompts — they are redundant and can hurt. Reduce few-shot examples (zero-shot first). System messages become developer messages; for Markdown, prepend `Formatting re-enabled` if needed. Plan a reasoning-token budget (≥ ~25,000 reserved). Use `reasoning_effort` as a tuning knob, not as the primary quality lever. Watch the hallucination risk on fact-heavy tasks (more claims → more potential errors).
- **AWAY FROM o3 to a GPT-5.x reasoning successor** (official replacement `gpt-5.6-sol`): keep effort control — on the Responses API `reasoning.effort`, for gpt-5.6-sol `none | low | medium (default) | high | xhigh | max` — and adopt o3's current level as the baseline (the GPT-5.6 docs phrase this as "preserve your current reasoning effort as the baseline" for migrations from GPT-5.5/5.4). **Do not** add CoT or planning scaffolding: the target is also a reasoning model, to which you give the task, constraints and output format instead of prescribing intermediate steps. Keep the developer-message contract (tool boundaries, critical rules up front).
- **AWAY FROM o3 to a non-reasoning GPT model** (e.g. `gpt-4.1`, per the model page "Smartest non-reasoning model" without a reasoning step): `reasoning_effort` is dropped; explicit CoT / planning prompting may be needed again (the GPT-4.1 guide: "GPT-4.1 is not a reasoning model", induce step-by-step planning via the prompt). Typical pattern per OpenAI: o-series for planning/decisions, GPT models for execution — many workflows combine both.
