# GPT-6 Astra

## Reasoning / Thinking
- `reasoning.effort` accepts `low | medium | high | xhigh | max`. **`none` is not supported** — the value is rejected with HTTP 400. Docs instruction for those switching: "When migrating from `minimal`, or from `none` to GPT-6 Astra or GPT-6.1 Sol, start with `low` and compare results."
- A model-specific default effort is not documented (unverified) — always set `reasoning.effort` explicitly instead of assuming an inherited value.
- `reasoning.mode`: `standard` (Default) | `pro` — per the reasoning guide "GPT-5.6 and GPT-6 models support `standard` and `pro` reasoning modes in the Responses API" (documented for the Responses API only). Mode and effort are independent; `pro` does more model work at higher latency and token usage. `configuration_update` (see below) is documented only in standard mode with a single agent.
- `reasoning.context`: `auto` (Default) | `current_turn` | `all_turns` — controls whether reasoning from earlier turns is rendered into the next sample; the response reports in the field `reasoning.context` which mode actually applied. The reasoning guide lists `all_turns` only for GPT-5.6 models and GPT-6.1 Sol; for Astra the value is not documented (unverified) — set `auto` and check the response field.
- `reasoning.summary: "auto"` returns the most detailed summary available (opt-in; summaries sit in the `summary` array of the reasoning output item). Raw chain-of-thought is not visible via the API; reasoning tokens still occupy context and are **billed as output tokens**. `max_output_tokens` caps reasoning and answer together; OpenAI recommends reserving at least 25,000 tokens for reasoning and output to start with.
- New compared with the GPT-5.6 family: effort can be adjusted **mid-conversation** via `configuration_update` items without rewriting the prompt — depth escalation therefore belongs in orchestration, not in the prompt text. Limits per the docs: only the GPT-6 family in standard mode (single agent); two `configuration_update` items must not directly follow each other (the API rejects that); do not combine with automatic compaction/truncation (`/responses/compact` also rejects such histories — set a fresh update after explicit compaction); keep request-level `reasoning.effort` unchanged (prompt caching); the response continues to report the request value.

## Prompting Style
- OpenAI describes Astra as "stronger at general instruction following" and "better able to follow longer instructions, but can also be more sensitive to information in context". Long, structured instruction blocks are therefore workable — but attached context (files, tool results, skills) weighs more heavily than with predecessors.
- **Grant autonomy explicitly.** The model "is more likely to ask the user a question when additional input could materially change the result". Counter-measure per the docs: instruct it to "bias towards action and carry the user's intended task to completion", declare phrasing such as "can you…"/"help me…" explicitly as a work order, and only ask for approval after "a concrete, reviewable result".
- **Spell out precedence.** Because Astra reacts more sensitively to instructions in skills and other files, the docs recommend the literal sentence: "The user's instructions take precedence over guidelines provided in a skill." Additionally require transparency — on a conflict the model should name the file and quote the conflicting passage. Review accessible files for behaviour-shaping instructions before migrating.
- **Explicitly request prose**, otherwise Astra produces lists, tables and Markdown. Docs wording: "Default to using clear, concise paragraphs, each developing one main idea."
- Style negative list from the docs: actively forbid "slop words" (e.g. "Bottom Line", "leverage", "it's worth noting"), contrastive framing ("X, not Y") and invented compound labels.
- **Actively instruct delegation** rather than capping it: Astra delegates too rarely in multi-agent setups. Recommended prompt building block: "If at any point you can parallelize work by delegating tasks to another agent … you should do so."
- **Calibrate test scope** instead of writing "test thoroughly": "Do not write tests for reversible, low-impact changes", and widen test scope only when "new changes, failures, or unresolved concerns justify it".

## Strengths & Weaknesses (prompt-relevant)
- Strengths: per the docs "state-of-the-art performance in computer use, browsing, software engineering, science, and professional work" at lower estimated API cost per task ("Its estimated API cost per task was lower than earlier models despite its higher per-token pricing."); positioned as "our most capable model, built for the hardest end-to-end work", carrying complex tasks "from an initial request to a finished result". Large tool set (`web_search`, `file_search`, `image_generation`, `code_interpreter`, `hosted_shell`, `apply_patch`, `skills`, `computer_use`, `mcp`, `tool_search`), 1.05M context, async tool calling (`async: true` on the function) for continued reasoning during tool execution, and mid-turn steering over WebSocket that accepts incoming corrections without discarding finished work.
- Weaknesses/quirks that must be compensated in the prompt: unnecessary pauses to ask questions ("This can cause it to stop when the user may expect it to make reasonable assumptions"); over-testing small changes ("For smaller tasks, this can result in broader tests than the task requires"); tendency toward long, heavily formatted answers and "recurring phrases across sessions"; heightened sensitivity to instructions in skills/files; too-rare delegation.
- Operational constraints: no `none` effort, no sampling parameters, tool calling only via the Responses API, and under EU data residency Astra supports neither `service_tier: "fast"` nor `service_tier: "priority"` (choose standard processing there). Ultrafast mode (`service_tier: "ultrafast"`, since 29 Sep 2026) only with US data residency or Global Processing; Fast mode for Astra has no latency SLA. Requests additionally pass through asynchronous misalignment monitoring.
- Rollout: release on 2026-09-03; as of 2026-10-13 the API docs carry no limited-access notice and document the model as generally available. The staged rollout form of the first days (first selected organisations, then wider across ChatGPT tiers, API and cloud partners) is not verified on the fetched doc pages (unverified) — do not read it as meaning the model was open to all developers on day one.

## Output & Format Conventions
- Context window 1,050,000 tokens, of which max. 922,000 input and 128,000 output. Knowledge cutoff: 30 Apr 2026.
- Prices: $10 / MTok input, $50 / MTok output, cached input $1, cache writes $12.50. **Price cliff at 272K input tokens**: above it, 2× input/cache rates and 1.5× output rates apply to the entire request. Batch/Flex at 50% of the standard rate, Fast mode 2×.
- Endpoints: Chat Completions, Responses, Batch. Not supported: Realtime, Assistants, fine-tuning, embeddings, image generation endpoint, videos, audio, moderation and legacy completions.
- Features: `streaming`, `structured_outputs`, `function_calling`, `file_search`, `image_input`, `web_search`, `prompt_caching`.
- Prompt caching is configured via `prompt_cache_options.ttl` (e.g. `"30m"`) — `prompt_cache_retention` is the superseded predecessor.
- Rate limits (Grow, the highest of the three tiers Build/Launch/Grow in effect since 6 Oct 2026): 15,000 RPM, 40M TPM, 15B batch queue limit.
- `text.verbosity` (`low` | `medium` | `high`) is usable with Astra: the deployment checklist shows `text: { verbosity: "low" }` on `gpt-6-astra` and calls the parameter "the main lever for balancing brevity against completeness" — set the default level of detail there, and define content, structure and length in the prompt.
- Enforce the format contract via **Structured Outputs** or an explicit prose instruction; without either, the answer drifts into verbose, list- and table-heavy Markdown.

## Migration Notes
- **AWAY FROM gpt-6-astra**: re-evaluate the autonomy, precedence and prose building blocks — they compensate for Astra quirks and are superfluous ballast on target models without the tendency to ask questions. Conversely, re-add: explicit test and verification steps (Astra tests unprompted and thoroughly), structure/format requirements if the target does not format on its own, and a delegation **cap** instead of a delegation prompt if the target delegates more readily. Technically: remove `reasoning.mode`/`reasoning.context`/`configuration_update`, `async: true` and mid-turn steering; reintroduce sampling parameters (`temperature`, `top_p`) only if the target knows them; rewrite `prompt_cache_options.ttl` into the target's cache syntax; scale the 1.05M context budget back to the smaller target window.
- **TO gpt-6-astra**: (1) set `model` to `gpt-6-astra`. (2) Replace `reasoning.effort: none`/`minimal` with `low` and compare results — there is no zero-thinking fast path here. (3) Move tool calling to the **Responses API**; otherwise Chat Completions remains usable but carries no tools. (4) Remove `temperature`, `top_p`, `top_logprobs` (and `logprobs` on Chat Completions). (5) `prompt_cache_retention` → `prompt_cache_options.ttl`. (6) Add the autonomy building block, otherwise the model stops to ask. (7) Write the precedence rule against skills/files into the system prompt and check bundled files for conflicting instructions. (8) Strip "be thorough"/"double-check" lines inherited from predecessor models and cap the test scope instead. (9) Allow delegation actively rather than capping it. (10) Set a verbosity counterweight (prose sentence plus slop-word ban). (11) Re-size `max_output_tokens`, since reasoning tokens count. (12) Check prompts above 272K input tokens against the price cliff. (13) With EU data residency remove `service_tier: "fast"` and `service_tier: "priority"` — both are not supported there; `service_tier: "ultrafast"` is likewise unavailable there (US residency/Global only). (14) An existing `reasoning.mode: "pro"` (e.g. from gpt-5.6-sol) can stay, but is documented only for the Responses API. Together with `configuration_update` it is not documented, so choose standard mode there. (15) Carry over an existing `text.verbosity` value (e.g. from gpt-5.6-sol/-terra) and check against the deployment checklist whether blanket "Be concise" lines still help alongside it.
